# ADR-0003: Logical layer is abstract; deployment layer is concrete

| Field | Value |

## Context

The phase-1 model was flat and repo-centric: the open lakehouse was one system,
the five repos were containers grouped by "plane." That couldn't express three
things we need:

1. **Two altitudes of one architecture** — an abstract reference lakehouse
   (catalog, query engine, table format, object storage, policy engine) *and* our
   concrete services, where the concrete is a *realization* of the abstract.
2. **Multiple deployment topologies** with different trust assumptions, where
   **enforcement location changes with the deployment** (trusted-compute enforces
   full FGAC in-plan; a vended credential to an external engine bypasses FGAC;
   the browser uses signed-URL/proxy).
3. **Cross-cutting governance** — the zero-trust points (PAP/PDP/PEP/PIP/PA) live
   in *different services*, and one service plays *several* points.

## Considered Options

- **Keep the flat repo-centric model** — simple, but conflates the reference
  architecture with our implementation and can't model deployment trust topologies.
- **Two logical systems (reference + implementation) linked by `realizes` edges** —
  makes both browsable, but duplicates structure and doesn't use LikeC4's
  deployment strength; trust topologies still aren't first-class.
- **Logical = abstract, deployment = concrete** — the logical model holds only
  technology-agnostic capabilities + governance roles; our repos are deployment
  `instanceOf`s that realize them across topologies.

## Decision

We chose **logical = abstract, deployment = concrete**. The logical model carries
no repo/service/infra names; each `service`/`gateway` deployment node `instanceOf`s
the logical capabilities and governance roles it realizes (one node can realize
several — e.g. hydrofoil = queryEngine + PDP + PEP). Three trust-differentiated
deployment topologies (`olaiNative`, `externalEngine`, `browserWasm`) show who
plays each role and where enforcement happens. The Envoy gateway (generated by
trestle's `stack-topology`) is modeled as the deployment node where the platform
manifests as **one cohesive API surface**. Designed-but-not-built work is tagged
`#designed`/`#prototype` (renders amber) so the model never overstates maturity.

LikeC4 has no reference-architecture "blueprint/implements" primitive yet, so the
abstract→concrete link is expressed via deployment `instanceOf` (not a logical
`implements` keyword).

## Consequences

### Positive
- The reference architecture is clean and reusable; our implementation is one
  realization of it. Deployment topologies (and their trust differences) are
  first-class and diagrammable.
- Governance decomposition is modeled once (logical) and mapped per topology.
- Maturity honesty is built into the model, not just prose.

### Negative / Trade-offs
- Repos are no longer browsable as standalone logical boxes — you read them via
  the deployment views. (Their identity lives in `metadata.sourceRepo` + design docs.)
- More layers to keep coherent; the `/update-architecture` skill and README encode
  the layer→file map to manage this.
- Ordering rules inside deployment nodes (metadata/link before `instanceOf`) are a
  minor authoring gotcha, documented in the README.

## Amendment (2026-10-16)

Accepted 2026-10-16 with the Trestle convergence P1 model refactor.

The Decision above stands. Two things have changed around it, and the Trestle
convergence ([design](../../docs/design/trestle-model-convergence.md)) needs a
third stated explicitly.

**The model no longer has the three topologies or the governance roles.** #73
removed `logical/governance.likec4`, the PAP/PDP/PEP/PIP/PA elements, and the
`olaiNative`/`externalEngine`/`browserWasm` deployments. The only modeled
deployment environment is `trustedCompute`. The zero-trust decomposition and the
credential-vending bypass are prose in `design/governance.md` and
`design/deployments.md`.

**The logical layer has two parts with different rules.**

- The **abstract reference architecture** (capabilities, asset kinds, and the
  concerns of [ADR-0007](./ADR-0007-cross-cutting-concerns.md)) names no
  technology. That is the rule this ADR set.
- The **technology catalog** ([ADR-0004](./ADR-0004-capability-specification-implementation.md))
  names specifications and software implementations, including first-party
  software (`omnigent`, `headwaters`). It is still logical:
  implementations are types of software, not running things.

**Deployment instances are configured occurrences of implementations.** A
deployment node `instanceOf` an implementation where one is modeled, and a
capability only where no implementation is (`trustedCompute`'s `headwaters`
points at its implementation; nodes whose software isn't in the technology
catalog still point at capabilities). Deployment fragments
generated from Trestle plans
([factory ADR-0003](../../docs/decisions/ADR-0003-trestle-generated-environments.md))
always point at implementations, so each generated node reaches its
capabilities through the implementation's `implements` and `realizes` edges.
