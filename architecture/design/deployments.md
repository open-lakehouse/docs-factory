# Deployments (the concrete layer)

Our repos manifest as **deployment instances** that realize the abstract
capabilities ([`reference-architecture.md`](./reference-architecture.md)). One
service can play several logical roles — e.g. hydrofoil is the query engine and
also embeds the policy decision and enforcement points. The model holds **one**
deployment environment, `trustedCompute` (`model/deployment/deployments.likec4`,
view `trustedComputeDeploy`). The untrusted cases below are prose: they explain
where enforcement moves, but they aren't modeled environments.

## `trustedCompute` — the reference deployment

Inside the trusted boundary:

| Node | Kind | `instanceOf` | Role |
|---|---|---|---|
| **hydrofoil** | service | `hydrofoil` | The catalog-native query engine; enforces full FGAC in-plan, embedding breakwater's decide/enforce split. |
| **mangrove** | service | `mangrove` | Governs securables, serves resource facts, and vends short-lived scoped credentials after an authorize check. |
| **headwaters** | service | `headwaters` | Captures column-level lineage at planning time. Its dynamic lineage / taint input to policy decisions is designed, not built. |
| Object storage | datastore | `lakehouse.objectStorage` | S3-compatible storage for table files. |
| Postgres | datastore | — | Relational store backing the catalog and lineage services. |

Which zero-trust point each service plays is described in
[`governance.md`](./governance.md).

## The gateway — where the platform manifests

An **Envoy gateway** (generated by trestle's `stack-topology` crate,
`olai-stack-topology`) fronts a trestle-generated stack. It is the platform's
**one cohesive API surface**: a documented invariant that *everything goes
through the gateway*. Envoy path-multiplexes the backends (catalog, lineage,
experiment-tracking, object stores) onto a single listener, plus a `/` catch-all
to the app; a prefix collision is a hard error. It is a **central gateway, not
per-service sidecars**.

With `ENVOY_AUTH` on, the gateway also becomes an **edge PEP** — an
`ext_authz`/Authelia forward-auth filter (fail-closed; strips client-forged
identity headers, re-adds auth-asserted ones). This is built but opt-in.

**Addressing varies by caller vantage** (in-container vs host vs in-process
desktop) — the same logical topology resolves to different URLs depending on where
the caller sits. `stack-topology` makes that a single tested model.

The gateway is not yet a node in `trustedCompute`.

## Outside the boundary (not modeled)

**External engine (credential vending).** An external engine isn't an instance
of hydrofoil, so the `#partial` fine-grained-access contribution is absent:
mangrove vends a short-lived scoped
credential to an external, untrusted engine (Spark, Trino, a notebook) after a
*coarse* authorize check; that engine then reads raw files directly. **Row
filters and column masks are bypassed**; only coarse access is enforced. The
non-vendable-governed-table guard (refuse to vend a raw credential for a governed
table) is the designed mitigation. The logical `credentialVending` dynamic view
shows the vending sequence itself.

**Browser (WASM), prototype.** A client-side WASM query engine runs in the
untrusted browser. The catalog issues signed URLs or proxies bytes rather than
vending raw credentials, so no raw cloud secrets reach the browser.

## Generated docs environments (planned)

The docs environments under `envs/` will be generated by Trestle and projected
into the deployment layer as their own environments, separate from the
narrative `trustedCompute`; see
[factory ADR-0003](../../docs/decisions/ADR-0003-trestle-generated-environments.md).

## What isn't modeled

`stack-topology` generates **local Docker Compose + Envoy** only. There is **no
Databricks-Apps deployment** — only a local `databricks-emulator-env` env
contract and Databricks-shaped URL paths at the gateway (to emulate the
Databricks edge locally). A real Databricks-Apps deployment is future work.
