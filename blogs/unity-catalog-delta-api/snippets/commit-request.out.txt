# The create -> commit lifecycle on the wire — real request bodies captured from
# Delta-Spark's traffic to the UC Delta API (v0.5.0), 2026-07-10. Captured by
# proxying Delta-Spark's HTTP to the server and dumping every POST body, then
# running read_write_delta_spark.py (table `events2`). NOT hand-written.
#
# This is the §5 centerpiece: intent-based, atomic, server-validated updates over
# ONE overloaded endpoint. Note the two-RPC create rule (staging -> promote) vs
# the single-RPC commit on an existing table.

## 1. POST .../staging-tables — allocate a managed table (client sends just the name)
$ POST /api/2.1/unity-catalog/delta/v1/catalogs/unity/schemas/default/staging-tables
{
  "name": "events2"
}
# -> the server RESPONDS with the vended file:// location + the feature-advertisement
#    payload (required/suggested protocol + properties). See the response in
#    api-transcripts.out.txt ("POST staging-tables").

## 3. POST .../tables/events2 — the atomic commit (INSERT INTO): one overloaded endpoint
$ POST /api/2.1/unity-catalog/delta/v1/catalogs/unity/schemas/default/tables/events2
{
  "requirements": [
    {
      "type": "assert-table-uuid",
      "uuid": "1f47e3b8-7fb8-413c-9d9d-20f2ab75b908"
    }
  ],
  "updates": [
    {
      "action": "add-commit",
      "commit": {
        "version": 1,
        "timestamp": 1783665699029,
        "file-name": "00000000000000000001.63e70f6f-eb63-4913-a1e3-2c9a973ea726.json",
        "file-size": 1773,
        "file-modification-timestamp": 1783665699076
      }
    },
    {
      "action": "set-latest-backfilled-version",
      "latest-published-version": 0
    }
  ]
}
# THE key artifact: `requirements` carries the optimistic-concurrency guard
# (assert-table-uuid — assert-etag appears here too on property/schema updates),
# and `updates` is the intent list. The client writes the Delta commit file first,
# then this RPC ratifies it (add-commit) — Delta's "client-writes-commit-then-
# catalog-ratifies" flow, guarded + validated server-side.
