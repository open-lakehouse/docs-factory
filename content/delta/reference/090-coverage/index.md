This page records what each engine can do with a Delta table and how far the
docs cover each journey. It's private: reviewers see it in the factory app, and
it's never emitted. The public "Features and engine support" (R01) and "Choose
an engine or client" (R10) pages are derived from it. Scope, ids, and journeys
come from the [documentation plan][plan].

## How to read and update this page

The journey tables below are generated from the journey catalog
([`architecture/journeys/`](../../../../architecture/journeys/README.md)), this
project's [`compatibility.yml`](../../compatibility.yml), and the claims in each
page's scripts (`uv run docsnip compat --fix`); edit those, never the tables. The
factory app's Plan → Compatibility page shows the same cells with each
one's proofs and evidence.

| Cell | Meaning |
| --- | --- |
| ✓ | A script on the linked page does the journey. "(draft)": that page isn't `ready`, so its script doesn't gate CI yet. |
| ✗ | It doesn't work: a script asserts the failure and its error string (linked to its page), or `evidence` says so (linked to the source). |
| docs | The engine's docs or source say it works. Not verified here. |
| — | Unknown. The [open checks](#open-checks) list the ones that matter most. |

- Only a script makes a cell ✓. A PR that adds or changes a script adds the
  `claims` for what it proves.
- A negative is tested only when a script asserts the failure and its error
  string, so CI flags the cell when an engine adds support.
- Unproven cells come from `architecture/journeys/evidence.yml`, each with the
  source it came from and the API the engine's docs name.
- The hand-written round-trip grid further down still uses `tested`,
  `documented`, `no`, and `?` in the same senses.
- Spark SQL and PySpark run on the same engine, so the table-feature tables
  have one Spark column.

## Engines and versions

The pins live in [`release.yml`](../../release.yml): Delta Spark 4.4.0 on
PySpark 4.2.0, the `deltalake` Python package 1.6.6 and Rust crate 1.1.1, and
DuckDB 1.5.6. A `tested` cell ran with them unless it says otherwise.

| Interface | Install | Cells refer to |
| --- | --- | --- |
| Spark · SQL | `spark-sql` from the pip `pyspark` wheel, with `io.delta:delta-spark_2.13` | `tested`: the Delta pages, path-based tables. Also `tested` through UC, where the UC pages pin `delta-spark` 4.3.1 on PySpark 4.1.0. `documented`: Delta 4.4.0 ([release][dd-4.4]). |
| Spark · Python | `pip install delta-spark`, then `configure_spark_with_delta_pip` | Same as Spark SQL. |
| delta-rs · Python | `pip install deltalake` | `tested`: the Delta pages. `documented`: 1.6.6 source ([table.py][dr-table], [feature table][dr-features]). |
| delta-rs · Rust | `cargo add deltalake --features datafusion` | `tested`: the Delta pages. `documented`: the 1.1.1 crate source ([operations][dr-rust-ops]). |
| DuckDB · SQL | `INSTALL delta; LOAD delta;` | `tested`: the Delta pages, core `delta` extension, path-based tables. Also `tested` through UC: DuckDB 1.5.6 with `unity_catalog` from `core_nightly`. `documented`: the [`delta` extension page][duck]. |

Not tracked yet: Polars, pandas, Daft, DataFusion on its own, Delta Kernel (Rust and Java), Trino, Flink, Iceberg readers through UniForm.

## Open checks

Ordered by how many pages or decisions they unblock.

1. **What a DuckDB append does to a table with constraints, generated
   columns, or deletion vectors.** If it writes past a `CHECK` constraint,
   H53 and H13 need a `:::warning` saying so.
2. **Whether DuckDB and deltalake appends are safe next to Spark writers on
   S3**, and with which locking setup (H27, H53).
3. **Which writer features deltalake commits to correctly**: deletion vectors,
   row tracking, `allowColumnDefaults`, clustering, `inCommitTimestamp`.
   `alter.add_feature()` enables some of them, which isn't the same as
   writing them correctly.
4. **Reader support for `columnMapping`, `deletionVectors`, `v2Checkpoint`,
   `typeWidening`, and `variantType`** in deltalake and DuckDB. A cross-engine
   script (Spark writes, the other engines read) settles most of the table
   above.
5. **Write a deletion vector and a v2 checkpoint on a UC managed table.** The
   UC Spark tutorial asserts all six features its managed table enables, but
   its DELETE drops a whole file and it never checkpoints, so neither feature
   is exercised yet.
6. **Spark `timestampNtz` and `variantType`**: Spark is the reference writer,
   but docs.delta.io has no page for either. Find the release that added
   each, then test it.
7. **Whether Spark reads a table after a DuckDB append.** DuckDB's commit
   records operation `UNKNOWN` and no `isBlindAppend`; deltalake reads it.
   One more driver step settles the last `?` in the round-trip table.
