# Unity Catalog: upstream asks

Changes we'd ask of the Unity Catalog project (server, connectors, and AI
packages) because a docs page has to work around their absence. Each ask names
the evidence script that pins today's behavior, so the release that delivers
it flips an assert and tells us which page to simplify.

The deployment asks drafted for UC 0.7 (U1–U8, C1–C7, PR #186) never landed on
`main`; fold them in here if that work resumes.

| ID | Component | Ask | Why (the page's workaround) | Evidence |
| --- | --- | --- | --- | --- |
| F1 | Spark connector (`unitycatalog-spark`) | Implement Spark's `FunctionCatalog` on `UCSingleCatalog`: resolve `catalog.schema.function` for `EXTERNAL` Python functions (`SELECT`, `SHOW FUNCTIONS`, `DESCRIBE FUNCTION`, `spark.catalog.listFunctions`), and ideally `CREATE FUNCTION` / `DROP FUNCTION`. | Every function statement on a catalog name fails: calls, `SHOW FUNCTIONS`, `DESCRIBE FUNCTION`, and the catalog API with `MISSING_CATALOG_ABILITY.FUNCTIONS`, `CREATE FUNCTION` with `MISSING_CATALOG_ABILITY.CREATE_FUNCTION`, and `DROP FUNCTION` with `MISSING_CATALOG_ABILITY.FUNCTIONS` on 4.1 and `MISSING_CATALOG_ABILITY.DROP_FUNCTION` on 4.2. So H54 fetches the function with `unitycatalog-ai` and registers a session UDF. That copy has no defaults and runs without contacting the catalog, so a replace or delete doesn't reach it. | `content/unitycatalog/how-to/028-spark-functions/snippets/spark_functions.py` `_native_resolution_fails`, `spark42_functions.py`; [`UCSingleCatalog.scala`](https://github.com/unitycatalog/unitycatalog/blob/v0.7.0/connectors/spark/src/main/scala/io/unitycatalog/spark/UCSingleCatalog.scala#L43-L47) |
| F2 | Server, engines, `unitycatalog-ai` | Give `routine_body = SQL` functions an executor: at least one OSS engine (Spark through F1, or DuckDB's `unity_catalog`) that evaluates the stored SQL body, or a server-side rejection of SQL bodies until one exists. | The server stores SQL-body functions, but `unitycatalog-ai` refuses them (`NotImplementedError: routine_body SQL is not supported…`), Spark can't resolve any catalog function, and the `uc` CLI runs any body as Python. A reader can register a function nothing runs. R01 records it. | `spark_functions.py` `_sql_body_functions`; [`python_engine.py`](https://github.com/unitycatalog/unitycatalog/blob/v0.7.0/etc/data/function/python_engine.py#L8-L25) |
| F3 | `unitycatalog-ai` | Make `get_function_as_callable` default to a function that pickles by value (don't register it in `execution_utils`' globals by default), and keep parameter defaults in the rebuilt signature. | With the default `register_function=True`, a Spark UDF built from the callable fails on every worker (`AttributeError: Can't get attribute 'order_total' on <module 'unitycatalog.ai.core.utils.execution_utils'>`); H54 has to pass `register_function=False`. Missing defaults make SQL calls pass every argument. | `spark_functions.py` `_default_registration_fails`, `_udf_edges`; `how-to/018-manage-python-functions/snippets/functions.py` (defaults) |
| F4 | `unitycatalog-ai` | Derive a function's comment and parameter comments from the signature, such as `Annotated[float, Field(description=…)]` the way Pydantic does, and accept the common docstring dialects (Google, NumPy, reST/Sphinx), for example through `docstring_parser`, instead of parsing Google-style `Args:` only. | The tool and argument descriptions a model reads come from the docstring, so H11, H13, H14, and H51 tell readers to write a Google-style docstring with an `Args:` section. A function with no description is rejected with `ValueError`, and `Args:` entries that don't match the signature only warn, so those parameters get no description. | `content/unitycatalog/how-to/018-manage-python-functions/snippets/signatures.py` (`no_docstring`, `only_args`, `mismatched_docstring`) |
| K1 | Server (credential encryption) | Accept decrypt-only previous keys next to `server.credential-encryption-key` (for example `server.credential-decryption-keys`), and pick the key by the key id each stored value already carries (`v1:<key id>:…`). New values use the active key. | `EncryptedCredentialSecretStore.load` rejects any value whose key id isn't the server's, so a rotation (H56) makes every `s3_compatible_access_key` credential unusable from the restart until its secret is supplied again, and there's no going back to the old key once one is. Operators must hold every plaintext secret, or create new key pairs, to rotate. | `content/unitycatalog/how-to/030-credential-encryption-key/snippets/encryption_key_cli.py` (`_vend_fails` after `rotate`, `_old_key_unreadable`); [`EncryptedCredentialSecretStore.java`](https://github.com/unitycatalog/unitycatalog/blob/main/server/src/main/java/io/unitycatalog/server/persist/secret/EncryptedCredentialSecretStore.java) |
| K2 | Server (credential encryption) | Re-encrypt every stored value under the active key without the plaintext supplied again: a server command or startup flag beside `--upgrade-schema`, which needs K1. Make the startup scan (`findUnreadableSecrets`) also report how many values each key id still holds, so an operator knows when an old key can be retired. | H56 has an operator update each credential with its secret, and check that a start logs no `Cannot read the stored secret` warning. Nothing reports which key a readable value uses. | `encryption_key_cli.py` (`resupply`, `_warnings`) |
| K3 | Server (credential encryption) | Make the secret store pluggable: `CredentialSecretStore.from` selects a provider by configuration (for example a `ServiceLoader`), so a deployment can wrap data keys with a KMS or keep secrets in Vault. A `v2` envelope format can sit beside `v1`. | The interface exists, and its Javadoc anticipates a store outside the database, but `from` always returns the AES-GCM store, so the key has to be in the server's environment. | [`CredentialSecretStore.java`](https://github.com/unitycatalog/unitycatalog/blob/main/server/src/main/java/io/unitycatalog/server/persist/secret/CredentialSecretStore.java) |
| K4 | Server (credential encryption) | Route the other secrets the server keeps through the same store, and read the key whether or not `server.s3-compatible-storage.enabled` is on. | Only the `secret_access_key` of `s3_compatible_access_key` credentials is encrypted; the key is read only when that experimental feature is on. | `EncryptedCredentialSecretStore.from` |
